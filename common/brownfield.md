# 既存システムの隣に作るとき（brownfield）

このリポジトリの 4 パターンは新規プロジェクト向けだが、実際には「古い本体の隣に新しい機能や別クライアントを足す」仕事が多い。
そのときエージェントは、既存コードの流儀に合わせようとして **既存の壊れ方まで真似る**。
2026-11 の FMS（車両管理 SaaS）での経験から、置き方、着手前の評価、新しいコードに課す規約を手順にまとめる。

ハーネスのリポジトリの `docs/guide.md` 第 2 部（プロジェクトの始め方）に重ねて使う。挟む場所は次のとおり。

| この文書の手順 | guide の手順との関係 |
|---|---|
| 1. 置き方を決める | 手順 0（始める前に決める）で一緒に決める |
| 2. 既存リポジトリを参照専用で置く | 手順 2（雛形とハーネスを置く）の前 |
| 3. 既存側を書き換えられないようにする | 手順 7（ハーネスが効いていることを確かめる）で一緒に確かめる |
| 4. 既存コードを測る | 手順 7 の後。最初の依頼として出す |
| 5. `CLAUDE.md` を埋める、6. 契約を起こす | 手順 8（「プロジェクト固有」を埋める）で |
| 7. 写すときの決まり、8. 既存側が変わったとき、9. 完了条件 | 日々の開発で |

例では、既存リポジトリを `legacy-fms`、新しいリポジトリを `my-app` と書く。

## 1. 置き方を決める

| 状況 | 置き方 |
|---|---|
| 新しいコンポーネントを作る（別クライアント、別サービス、置き換え先） | 新しいリポジトリを作り、既存リポジトリの **兄弟ディレクトリ** に置く。この文書の対象 |
| 既存リポジトリの中に機能を足す | 対象外。タイプの雛形は使えず、基底だけを入れる形になる。その使い方はまだ確かめていない |

```
work/
├── agent-dev-harness/   ハーネス。ここからコピーする
├── legacy-fms/          既存。参照専用の clone。エージェントは読むだけ
└── my-app/              新規。雛形とハーネスはここにだけ置く。claude はここで起動する
```

- **`claude` は新しいリポジトリのルートで起動する。** 親（`work/`）で起動しない。設定とフックは起動したディレクトリのものだけが読まれるので、親で起動するとガードが 1 つも効かない
- **既存リポジトリを新しいリポジトリの中に入れない**（サブディレクトリ、submodule）。既存のコードが検索に混ざり、エージェントがそれを手本にする
- **既存の clone は参照専用に、別に取る。** ふだん既存側の開発に使っている作業ディレクトリを指さない。書きかけの変更を読ませず、万一書き換えられても失うものが無いようにする
- **既存側にはハーネスを入れない。** `CLAUDE.md` も `.claude/` も足さない

## 2. 既存リポジトリを参照専用で置く

```bash
cd work
git clone <既存リポジトリの URL> legacy-fms
git -C legacy-fms rev-parse --short HEAD     # 基準にするコミット。手順 5 で CLAUDE.md に書く
```

この後、guide の手順 1〜6 で `my-app` を立ち上げ、`check` を緑にして最初のコミットまで済ませる。
既存を読ませるのはその後にする。立ち上げで出る問題と、既存から来る問題を混ぜない。

立ち上げたら、この文書を新しいリポジトリに置く。基底の `CLAUDE.md` が `docs/brownfield.md` を指している。

```bash
cd my-app
mkdir -p docs && cp ../agent-dev-harness/common/brownfield.md docs/brownfield.md
```

## 3. 既存側を書き換えられないようにする

雛形の `settings.json` は `Edit` と `Write` を全面的に許可している。何もしないと、エージェントは既存リポジトリのファイルも確認なしで書き換えられる。
新しいリポジトリの `.claude/settings.local.json` に次を書く。パスは人ごとに違うので、このファイルはコミットしない。

```json
{
  "permissions": {
    "additionalDirectories": ["/Users/you/work/legacy-fms"],
    "deny": ["Edit(//Users/you/work/legacy-fms/**)"]
  }
}
```

コミットされないことを確かめる。無視されていなければ `.gitignore` に足す。

```bash
git check-ignore -q .claude/settings.local.json || echo '.claude/settings.local.json' >> .gitignore
```

- **守りの要は `deny` の 1 行。** パスは `//` で始める絶対パスにする。`/` が 1 つだとプロジェクトのルートからの相対になり、既存側に当たらない。`Edit` の拒否は Write にも効く
- `additionalDirectories` は、既存側を読む場所として宣言する。追加したディレクトリの設定・フック・`CLAUDE.md` は読み込まれないので、既存側の流儀が指示として入ってくることは無い
- 起動時に `--add-dir` で渡す形は使わない。そちらは既存側の `.claude/` にあるスキルやサブエージェントを読み込む
- これは事故を防ぐガードレールで、Bash 経由の書き込みまでは止めきれない。越えられない境界にしたいときは、参照用の clone に push できる認証情報を持たせない

効いていることを確かめる。新しいリポジトリのルートで `claude` を起動し、次を頼む。

> Edit ツールで `../legacy-fms/README.md` の先頭に 1 行足して。拒否されたら、その文言をそのまま報告して。

`denied by your permission settings` を含む文言が返り、次のコマンドで何も出なければ効いている。

```bash
git -C ../legacy-fms status --short
```

## 4. 既存コードを測る（半日）

目的は「どこがコピーで増えているか」「唯一の定義場所がどこか」を知ること。機械的に測れるものから始める。
最初の依頼として、エージェントに測らせる。依頼の例。

> `../legacy-fms` を読んで、`docs/brownfield.md` 手順 4 の表の観点で測り、結果を `docs/legacy-assessment.md` に書いて。既存側は変更しない。数は grep の出力で裏づけ、推測で埋めない。

| 観点 | 測り方 | 旧 FMS での結果 |
|---|---|---|
| 業務ロジックのコピー | 同名関数の二重定義を grep。正規化した行の一致率をファイル対で比較 | 採点ロジック 2 系統（65% 一致）、月報 51%、Web と運営管理の認証系 40〜65% |
| レイヤ違反 | `proc.db.` / `query(` / `SELECT ` をハンドラ配下で grep | 直書き SQL 8 箇所、Redis キーの組み立て 6 箇所以上 |
| 入口の重複 | 認証・CORS・エラー応答のラッパーがいくつあるか | API 4 系統、CORS ヘッダ 4 回コピー（うち 1 箇所が構文違反） |
| 列挙値 | ロール番号・種別コードの直書き数と enum の参照数 | `case "1".."4"` が 20 箇所、enum は定義だけで参照 0 |
| 時刻変換 | `moment(`、`Date.UTC(`、`padLeft(2`、`substring(` の出現数 | サーバー 10 箇所以上、アプリ 20 箇所の手変換。同じ文字列を 2 通りに解釈 |
| 契約文書 | 文書の例と実装の応答項目を突き合わせる | 追記型で育ち、同じ節に矛盾（「写真は無し」と「写真を受け付ける」） |
| 安全網 | テスト数、lint、`strict`、CI | すべて無し。`any` 382 箇所 |

旧 FMS で使った grep。パターンは既存側の言語と書き方に合わせて直す。

```bash
cd ../legacy-fms
# ハンドラ配下の直書き SQL / Redis キー
grep -rn 'proc\.db\.\|queryRaw\|_threezero_alc' src/handler --include='*.ts'
# ロール番号・種別コードの直書き
grep -rn 'case "[1-4]"\|roleNo *== *["'"'"'][1-4]' src --include='*.ts' | wc -l
# 時刻の手変換
grep -rn 'moment\.\(utc\)\?(.*add\|Date\.UTC(\|padLeft(2\|substring(8, 10)' src lib --include='*.ts' --include='*.dart' | wc -l
# 同名関数の二重定義（export const の名前を集計）
grep -rhoE 'export const [A-Za-z_]+' src --include='*.ts' | sort | uniq -d
# 画面から API クライアント / ストアを直接触っている箇所（Flutter）
grep -rn '\.api\.\|widget\.api\|\.store\.\|\.uploader\.' lib/ui --include='*.dart'
```

`docs/legacy-assessment.md` に書くこと。

- 測った日と、既存リポジトリの基準コミット
- 観点ごとの数と、代表的な場所（パスと行）
- **真似ない流儀**：既存がコピーや直書きで増やしている書き方
- **唯一の定義場所の候補**：既存のどこに定義があるか、定義が無い概念はどれか
- 文書と実装の食い違い

結果は人が読む。どの流儀を真似ないか、定義をどこに置くかは人が決める。「どこに何があるべきか」の判断材料になり、同じコピー分岐をしそうなときに踏みとどまれる。

## 5. `CLAUDE.md` の「プロジェクト固有」を埋める

新しいコードでも、半年で同じ壊れ方が始まる。測った結果を `CLAUDE.md` の決まりに落とす。

| 欄 | 既存の隣に作るときに書くこと |
|---|---|
| 契約の段階、相手リポジトリ、契約の版 | 既存リポジトリの名前、基準コミット、契約文書の場所 |
| 外部連携と、ローカルでの代わり | 既存システムの API を手元で何に代えるか（スタブ、検証環境） |
| 外に出ている版 | 稼働中の既存システムの版。新しい側が合わせる相手 |
| 触ってはいけない場所 | `../legacy-fms` の全体。読むだけ |
| 依頼の入口と、状態・決定の記録先 | 既存側に変えてほしいことは `docs/legacy-requests.md` に書き、人が既存側に渡す |

加えて 2 つ足す。

**真似ない流儀の欄。** 手順 4 で決めたものを 3〜5 個、「プロジェクト固有」の末尾に 1 行で足す。基底の「既存コードの流儀に合わせる」より、こちらを優先する。

```
- 既存の流儀のうち真似ないもの：ロール番号を文字列で比べる / 時刻を substring で読む / 判定をクライアントで計算し直す
```

**「唯一の定義場所」の表への行。** タイプの表に、既存から来る概念の行を足す。「この概念の定義はここ」を名指しし、**「無ければここに新設してから使う」まで書く**。禁止だけ書くと、無いときにまた直書きされる。

| 概念 | 唯一の定義場所（例） |
|---|---|
| API 契約 | OpenAPI。手書き文書しか無いなら「同じ PR で上書き（日付つき追記で古い記述を残さない）」 |
| 判定ルール（しきい値・超過・権限範囲） | サーバーが判定し、結果を応答に含める。クライアントは表示するだけ |
| 列挙値（種別・状態・ロール） | 1 つの enum。外部表記への変換はその enum の拡張だけ |
| 時刻変換 | 1 ファイル。項目名の接尾辞で形式を示す（`*At` = ISO 8601、`*Time` = 現地の文字列） |
| 永続化のキー・行フォーマット | 1 モジュールに組み立てと解析を置く。`split("|")[n]` を他所に書かない |
| 環境差（ローカルのスタブ） | ビルド時の差し替え。共有コードに `if (STAGE === "local")` を書かない。やむを得なければ「本番との差分」一覧に追記 |

`CLAUDE.md` には決まりだけを書く。測った数字や経緯は `docs/legacy-assessment.md` に置く。

## 6. 契約を起こす

既存の API を新しい側から呼ぶときの手順。

| 既存側にあるもの | すること |
|---|---|
| OpenAPI | その版を取り込む。タイプの手順どおり |
| 手書きの文書だけ、または何も無い | 新しい側が使う範囲だけを OpenAPI に起こし、新しいリポジトリの `openapi/` に置く |

起こすときの決まり。

- **実装を正とする。** 文書と実装が食い違ったら実装に合わせ、食い違いを `docs/legacy-assessment.md` に残す
- ファイルの先頭に、写し元（ハンドラのパス）と基準コミットを `# SYNC:` で書く
- 型だけでなく意味も書く。どちらが判定するか、時刻の形式とタイムゾーンは何か。型として正しい IF を意味がすり抜けるのが、典型的な壊れ方になる
- 起こした契約が実際の応答と合っているかを、検証環境か記録した応答で 1 度は確かめる。この確かめ方は雛形に無く、まだ決まっていない

## 7. 既存から写すときの決まり

- 既存コードを複製して分岐させない。共通部分を関数に切り出して両方から呼ぶ
- 既存システムの挙動に合わせる必要がある値・文言は、コピー元を `// SYNC: <リポジトリ>/<パス> <関数名>` で記す。grep で拾えるようにする
- 既存の認証・権限チェックを「ほぼ同じ」で再実装しない。差分があるなら、既存側に引数を足してもらうよう `docs/legacy-requests.md` に書く
- 既存側を直せば済むことを、新しい側の回避コードで埋めない。これも依頼に書く

## 8. 既存側が変わったとき

写した値は、写し元が変わると黙ってずれる。既存側のリリースに合わせて、次を回す。

```bash
git -C ../legacy-fms pull
git grep -n 'SYNC:'                                                          # 写した箇所と、その写し元
git -C ../legacy-fms diff --stat <基準コミット>..HEAD -- <SYNC が指すパス>   # 写し元が変わったか
```

- 写し元が変わっていたら、写した側を直してテストを通す
- `CLAUDE.md` の基準コミットを新しいものに書き換える
- 既存側の構造が大きく変わったら、手順 4 を測り直す

## 9. 完了条件に足すもの

機械判定（テスト・型・lint）に加えて、人が確認する項目をチェックリストで持つ。

- [ ] 契約を変えたら、同じ PR で契約文書を上書きした
- [ ] 契約を変えたら、相手側リポジトリ（サーバー ↔ クライアント）の対応を同時に作ったか、未対応を PR 本文に書いた
- [ ] 既存システムから写した値には SYNC マーカーがある
- [ ] 既存リポジトリに変更が入っていない（`git -C ../legacy-fms status --short` が空）
- [ ] 既存側に頼むことは `docs/legacy-requests.md` に書いた
- [ ] 新しい TODO や「本番では別途対応」は引き継ぎ文書に書いた

## 確かめたこと、確かめていないこと

- **手順 3 の設定は実機で確かめた**（2026-11-18、Claude Code 2.1.282、一時ディレクトリ）。`deny` があると Edit は `File is in a directory that is denied by your permission settings.` で止まり、ファイルは変わらなかった。`deny` が無いと、`Edit` を全面許可した状態では、`additionalDirectories` の指定が有っても無くても、兄弟ディレクトリのファイルが確認なしで書き換わった
- `additionalDirectories` と `--add-dir` の違い、`//` で始めるパスの書式は、公式文書で確認しただけで、対話セッションでの挙動は試していない
- 手順 4 の測り方と、手順 5・7 の規約は、旧 FMS 1 件の経験から来ている
- 手順 1・2 の置き方、手順 6 と 8 は机上で書いたもので、実プロジェクトでは確かめていない
