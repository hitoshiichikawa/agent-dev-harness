# ガイド：考え方と、プロジェクトの始め方

この文書 1 つで、このリポジトリが何を実現しようとしているかと、実際にプロジェクトを始める手順が分かるようにする。
前半が考え方、後半が手順。細部は末尾の関連文書に任せ、ここには筋道だけを書く。

---

## 第 1 部　考え方

### 実現したいこと

AI エージェントに開発を任せることが主流になる。そのとき、うまくいくかどうかが「頼み方のうまさ」や「たまたま」で決まるのでは困る。
**成功を再現できるようにする**。うまくいったやり方を仕組みにして、次のプロジェクトは最初からその上で始める。

そのためにこのリポジトリは 3 つのものを持つ。

- **スケルトン**：作るものの種類ごとの雛形。技術の選定と、ディレクトリの構造が決めてある
- **ハーネス**：エージェントの周りに置く制約と検証。何を知らせ、何を禁じ、どうやって正しさを確かめるか
- **知見の蓄積**：各プロジェクトで得た知見と失敗を、ここへ戻して次に効かせる流れ

あらゆる開発をここから始め、得たものをここに戻す。ノウハウの置き場所を 1 つにする。

### 8 つの考え方

**1. 指示より仕組み。**
エージェントは指示を忘れることがあり、長い指示ほど 1 行あたりの効きが落ちる。仕組みは忘れない。
守らせたいことは、構造で間違えようがなくするか、フックや lint で機械的に止める。`CLAUDE.md` には「毎回間違えるから毎回言うこと」だけを書く。

**2. 完了は機械が決める。**
「できました」という報告を完了の根拠にしない。テスト・型・lint・生成コードの鮮度が通って初めて完了とする。
各プロジェクトは `check` という 1 つのコマンドでこれを確かめる。エージェントがファイルを編集したのに `check` を通さずに終わろうとすると、門番が止める。

**3. 壊せる操作は人が叩く。**
デプロイ、DB マイグレーションの適用、署名、ストア提出、強制 push はエージェントにさせない。フックが止め、「人間に依頼して」と返す。
ただしフックは事故を防ぐガードレールで、越えられない境界ではない。本番への到達のような境界は、認証情報を持たせない・ブランチ保護をかけるなど、権限の側で作る。

**4. エージェントがよく知っている技術を選ぶ。**
枯れていて採用例が多い構成は、エージェントが大量に学習している。尖った選択は精度を落とす。
スケルトンの技術は「今の時点で安定している標準」を基準に選び、選ばなかったものと理由を各パターンの README に残してある。

**5. 同じものを 2 か所に書かない。**
判定のルール、列挙値、時刻の変換、API の契約は、定義する場所を 1 つに決める。生成コードは手で直さず、元を直して再生成する。
禁止だけ書くと、定義が無いときにまた直書きされる。「無ければここに作る」まで名指しする。

**6. IF で区切り、人は IF を見る。**
システムは IF（契約）で区切ったコンポーネントに分ける。担当のエージェントは自分の中身と契約だけを、全体を統括するエージェントは契約と各コンポーネントの状態だけを持てば足りる。大きなシステムでも、誰のコンテキストも溢れない。
人の確認点も同じ場所に置く。人は契約の差分を必ず読み、実装の中身は機械判定と抜き取りで見る。これを標準とするが、人が実装を見ないことを是とできるかはガバナンスの問題を含み、まだ決めていない。

**7. 知見は戻す。足すだけでなく、削る。**
同じ間違いが 2 回起きたら、それはハーネスに足す材料になる。記録し、どこに入れるかを決めてから反映する。
1 件だけの知見は仮説として扱い、2 件目で確かめる。効いていない決まりは削る。

**8. 確かめていないものは信じない。**
机上で規約を磨いても、最初の実物で崩れる。このリポジトリの雛形は、実際にビルドして確かめたものではない。
ガードも同じで、試験を作って初めて、止めているつもりで止まっていなかったものが見つかった。効かない仕組みは、エラーにならず、ただ効かない。だから動かして確かめる。

### 全体の形

決まりは 3 段で継承する。上の段ほど変わりにくい。

```
汎用の基底   作業の進め方、完了の定義、禁止事項、共通のガード        common/
   ↓
タイプ       その種類の技術の規約、check の中身、人間専用の操作      web/ mobile-flutter/ desktop-mac/ desktop-windows-wpf/
   ↓
プロジェクト 目的、ドメインの用語、業務ルール、契約の段階、触れる範囲    各プロジェクトの CLAUDE.md 末尾
```

プロジェクトで書くのは最後の段だけにする。それより上に足したくなったことは、知見としてこのリポジトリに戻す。

## 第 2 部　プロジェクトの始め方

### 0. 始める前に決める

**何を作るか。** 種類からタイプを選ぶ。

| 作るもの | タイプ |
|---|---|
| ログインして使う業務系 web アプリ | `web/` |
| iOS / Android アプリ（web と同じ API を使う） | `mobile-flutter/` |
| スタンドアロンの mac アプリ | `desktop-mac/` |
| スタンドアロンの Windows アプリ | `desktop-windows-wpf/` |

mac と Windows のタイプは、その OS のローカルで Claude Code を動かす前提になる。

どれにも当てはまらないもの（バッチ、CLI など）は、`common/` の基底だけを使う。この使い方はまだ確かめていない。

**リポジトリをいくつにするか。** リリースの周期が同じものは同じリポジトリに、違うものは分ける。API と Web フロントは同居、モバイルは別にする。
分けたときに契約をどこに置くかは、契約を使うリポジトリの数で決まる（[`design.md`](design.md) 4 章の段階表）。

**既存システムの隣に作るか。** そうなら、先に [`common/brownfield.md`](../common/brownfield.md) の手順で既存コードを測る。エージェントは既存の壊れ方まで真似る。

### 1. 道具を揃える

- Claude Code、git、bash
- `jq`。フックが入力を読むのに使う。入れておく
- 選んだタイプのツールチェーン。各パターンの README の「決定事項」と「scaffold 手順」にある

### 2. 雛形とハーネスを置く

`<pattern>` を選んだタイプの名前に、`my-app` をプロジェクトの名前に読み替える。

```bash
git clone https://github.com/hitoshiichikawa/agent-dev-harness.git

# 雛形をコピーして新プロジェクトにする
cp -r agent-dev-harness/<pattern>/template my-app && cd my-app

# そのタイプの文脈と、権限・フック
cp    ../agent-dev-harness/<pattern>/CLAUDE.md CLAUDE.md
cp -r ../agent-dev-harness/<pattern>/.claude   .claude

# 基底を合流させる
cp    ../agent-dev-harness/common/CLAUDE.md     .claude/CLAUDE.common.md
cp -r ../agent-dev-harness/common/.claude/hooks .claude/hooks/common
```

Flutter だけは順序が違い、先に `flutter create` してから雛形を上書きする（[`mobile-flutter/README.md`](../mobile-flutter/README.md)）。

置いた後はこうなる。

```
my-app/
├── CLAUDE.md                    タイプの文脈。冒頭で基底を取り込み、末尾にプロジェクト固有の欄
├── .claude/
│   ├── CLAUDE.common.md         基底の文脈
│   ├── settings.json            権限の許可と拒否、フックの定義
│   ├── rules/                   ファイルごとの書き方。該当するファイルを開いたときだけ読まれる
│   └── hooks/
│       ├── common/              基底のガードと、check の門番
│       ├── post-edit.sh         編集のたびに走る整形と軽い検査
│       └── extra-deny.txt       そのタイプで止める操作
└── （雛形の中身）
```

### 3. アプリ本体を作る

雛形が持つのは、設定ファイル・ディレクトリの構造・各層 1 ファイルずつの最小コードだけ。アプリ本体は各ツールの scaffold で作る。
手順は各パターンの README の「scaffold 手順」に従う。

- プレースホルダを一括で置き換える。Go の module path（`github.com/ORG/APP/api`）、Swift と .NET の `MyApp`、Flutter の `my_app`
- `package.json` や `pubspec.yaml` に書いてあるバージョンは意図のメモ。パッケージマネージャに解決させ、ロックファイルを正とする

### 4. git を始める

```bash
git init
```

`check` より先に行う。生成コードの鮮度の検査と、`check` の門番が git を使う。git を始める前の `check` は、web と mobile では必ず落ちる。

### 5. `check` を緑にする

生成コードがあるタイプは先に生成し、追跡に入れてから完了条件を回す。

| タイプ | コマンド |
|---|---|
| `web/` | `task gen && git add -A && task check` |
| `mobile-flutter/` | `make gen && git add -A && make check` |
| `desktop-mac/` | `make gen && git add -A && make check` |
| `desktop-windows-wpf/` | `git add -A && make check` |

`git add` を先にするのは、鮮度の検査が「追跡している生成コード」と「再生成した結果」の差を見るため。追跡していないと差が見えず、検査が素通りする。

**最初は落ちる前提で臨む。** 雛形のコードは実際のビルドで確かめていないので、生成される型名や引数名とのずれが出る。ここで潰す。
直したことは `docs/harness-feedback.md` に書き留める。これが、このリポジトリに戻す最初の知見になる（手順 11）。

緑になったらコミットする。生成コードとロックファイルも含める。

```bash
git add -A && git commit -m "chore: 雛形から立ち上げ"
```

### 6. 権限を固める

フックに頼らない側の守りを入れる。フックは事故を防ぐガードレールで、境界ではない。

- リモートの `main` にブランチ保護をかける（強制 push の禁止、PR を必須にする）
- エージェントが動く環境に、本番に届く認証情報を置かない（クラウドの本番用の鍵、署名鍵、ストアの認証情報）

### 7. ハーネスが効いていることを確かめる

プロジェクトのルートで、ガードに直接入力を渡す。どちらも `BLOCKED` と表示され、終了コードが 2 になれば効いている。

```bash
echo '{"tool_input":{"command":"git push --force"}}' | CLAUDE_PROJECT_DIR="$PWD" bash .claude/hooks/common/guard-bash.sh; echo "終了コード $?"
```

```bash
printf '{"tool_input":{"file_path":"%s/.env"}}' "$PWD" | CLAUDE_PROJECT_DIR="$PWD" bash .claude/hooks/common/guard-edit.sh; echo "終了コード $?"
```

そのうえでプロジェクトのルートで `claude` を起動する。初回はフォルダを信頼するかを聞かれる。承認するまで、`settings.json` の許可ルールは効かない（拒否ルールとフックは最初から効く）。

### 8. `CLAUDE.md` の「プロジェクト固有」を埋める

毎プロジェクトで書くのはここだけ。欄は全タイプ共通の 10 個で、タイプ固有の欄（配布レーンなど）がその後ろに付く。
どれもコードからは読み取れず、エージェントが判断の拠り所にする情報にあたる。

- 目的と利用者、やらないこと
- ドメインの用語
- 主要なエンティティと関係（モバイルは主要画面と遷移）
- 破ってはならない業務ルール
- 契約の段階（0〜2）、相手リポジトリ、取り込んでいる契約の版
- 外部との連携と、ローカルでの代わり（スタブ）
- 環境（ローカル / 検証 / 本番）と、エージェントが届く範囲
- 外に出ている版（互換を保つ相手）
- 触ってはいけない場所
- 依頼の入口と、状態・決定の記録先

当てはまらない欄は消さずに「該当なし」と書く。1 欄は 1〜2 行に収める。長くなる説明は別の文書に書き、ここには場所だけを書く。
タイプが埋めてある欄（責任範囲と境界、コマンド、唯一の定義場所など 12 個）の一覧は [`design.md`](design.md) 2 章にある。

既存システムの隣に作るときは、「唯一の定義場所」の表もここに置く。「この概念の定義はここ。無ければここに作る」まで名指しする。

### 9. 最初の依頼を出す

普通に頼めばよい。たとえば「`examples` に `description` を足して、一覧と作成 API に反映して」。
あとは次のことが自動で起きる。

| いつ | 何が起きるか |
|---|---|
| セッションの冒頭 | `CLAUDE.md` が読まれ、責任範囲・コマンド・構成・依存の向き・定義の置き場所を知った状態で始まる |
| ファイルを開いたとき | そのファイルに当てはまる書き方の規約（`.claude/rules/`）が読み込まれる |
| ファイルを編集するたび | 整形と軽い検査が走り、落ちればその場でエージェントに返る |
| 禁じた操作をしようとしたとき | 止まり、「人間に依頼して」と返る。生成コード・`.env`・ロックファイルの編集も止まる |
| 終わろうとしたとき | 編集したのに `check` が通っていなければ止まり、`check` を回して直すよう返る |

3 ファイル以上を触る変更や、設計の判断を含む変更では、エージェントは先に計画を示す。DB スキーマの変更や新しい依存の追加などは、作業を止めて確認を取りに来る。

### 10. 人がやること

- **止められた操作を叩く。** マイグレーションの適用、デプロイ、署名、ストア提出。エージェントが「人間に依頼」と言ってきたら、内容を見て自分で実行する
- **PR をレビューする。** 契約（OpenAPI）の差分、マイグレーションの SQL、エージェントが確認を取りに来た判断は必ず読む。実装の中身は、`check` の結果と抜き取りで見る
- **警告を見逃さない。** 「check が通っていないまま終わった」という警告が出た回は、エージェントが何と言っていても完了ではない

### 11. 知見を戻す

プロジェクトで次のことが起きたら、エージェントか人が `docs/harness-feedback.md` に 1 件書き留める。

- 同じ指摘を 2 回した
- フックが止めるべきでないものを止めた、または止めるべきものを通した
- `CLAUDE.md` や雛形の記述が、実際と違っていた

区切りのよいところ（最初に `check` が緑になったとき、最初のリリースの後など）で、このリポジトリの [`learnings.md`](learnings.md) に移す。そこで行き先を決めて反映する。
プロジェクトの中でフックや設定を直して回避しない。直すのはこのリポジトリで、次のプロジェクトにも効く形にする。

### うまくいかないとき

| 症状 | 原因と対処 |
|---|---|
| 立ち上げ直後の `check` が、生成コードの検査で落ちる | `git init` の前に回している（手順 4）。または生成コードを `git add` していない（手順 5） |
| すべてのコマンドと編集が止まり、「No such file or directory」と出る | 手順 2 の最後の行（`hooks/common` のコピー）が漏れている。ガードは動けないとき、通さずに止める |
| エージェントが終わろうとするたびに `check` を促される | 編集した後に `check` が通っていない。直らないときは、エージェントがその旨を報告して 2 回目に止まれる。そのとき警告が出る |
| コミットで止まる | メッセージに、止める操作の名前（`cdk deploy`、`push --force` など）が入っている。言い換えるか、ファイルに書く |
| `.env.local` などが読めない | 仕様。読み書きできるのは `.env.example` だけ |
| 編集のたびに待たされる | 編集後のフックの検査が重い。フックは整形だけにして、検査は `check` に寄せる |
