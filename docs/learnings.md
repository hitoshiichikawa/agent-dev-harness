# 知見の記録

各プロジェクトで得た知見と失敗を、ここに 1 件ずつ記録する。記録してから、どこに入れるかを決める（考え方は [`design.md`](design.md) 6 章）。
`CLAUDE.md` に 1 行足したくなったら、その前にまずここに書く。

## 流れ

1. **プロジェクトで書き留める**。エージェントか人が、プロジェクトの `docs/harness-feedback.md` に 1 件追記する（`common/CLAUDE.md`「ハーネスへのフィードバック」）
2. **ここへ移す**。このリポジトリに、下の書式で 1 件足す。この時点では記録するだけでよい
3. **行き先を決めて反映する**。効きの強い順に検討し、決めた先を直す。記録の「行き先」と「反映」を埋める
   1. スケルトンの構造で、間違えようがなくする
   2. lint やフックで機械的に止める（ガードの穴なら、直す前に `tests/cases/` に 1 行足す）
   3. `CLAUDE.md` に 1 行足す
   4. 人間用のチェックリストに足す
4. **確かめる**。同じことが別のプロジェクトでも起きたら「根拠」に足す。反映したのに効かなかった、一度も引っかからなかった、と分かったら削り、その旨を記録に残す

## 書式

```markdown
### YYYY-MM-DD 何が起きたかを一言で

- **出どころ**：プロジェクト名とタイプ。PR や議論があればリンク
- **何が起きたか**：事実だけ。エージェントが何をして、何がまずかったか
- **なぜ起きたか**：分かる範囲で
- **層**：基底 / タイプ（どれか） / タイプ間の関係
- **行き先**：構造 / フック・lint / CLAUDE.md / チェックリスト / 見送り（理由）
- **根拠**：1 件（仮説） / 2 件以上（どのプロジェクトか）
- **反映**：未 / 済（PR へのリンク）
```

## 決まり

- **事実を書く**。評価や一般論を足さない。「気をつける」で終わる記録は行き先が決まっていない
- **1 件だけの知見は仮説**。反映してよいが、根拠が 1 件であることを残し、2 件目で確かめる
- **プロジェクト固有のものは入れない**。そのプロジェクトの `CLAUDE.md`「プロジェクト固有」に書く。ここに入れるのは、次のプロジェクトにも効くものだけ
- **層は「それが真である一番上」** にする。原則は基底に、置き場所の名指しはタイプに分ける
- 新しいものを上に足す

## 記録

### 2026-11-14 立ち上げ手順が、雛形の `check` と噛み合っていなかった

- **出どころ**：このリポジトリ。ガイドを書くときに、手順のコマンドを実際に動かして確かめた
- **何が起きたか**：README は「`check` が通ってから `git init`」としていた。しかし web と mobile の `check` は、生成コードの鮮度を `git diff` で見る。git を始める前は必ず落ち、始めた直後でも生成コードを追跡していなければ差が見えずに素通りする
- **なぜ起きたか**：手順も雛形も、通しで動かしたことがなかった
- **層**：タイプ（web、mobile-flutter）
- **行き先**：文書（README・ガイド・scaffold 手順の順序を `git init` → 生成 → `git add` → `check` に直す）。鮮度の検査が未追跡のファイルも見るようにすれば構造で防げるが、まだしていない
- **根拠**：1 件（このリポジトリ。コマンドを動かして確認）
- **反映**：済（文書のみ。この記録と同じ変更）

### 2026-11-14 エージェントが自分のガードを書き換えられる

- **出どころ**：このリポジトリのレビュー。プロジェクトではまだ起きていない
- **何が起きたか**：`guard-edit.sh` は `.claude/hooks/` と `.claude/settings.json` を守っていない。ガードに止められたエージェントが、ガードのほうを直して先へ進める状態にある
- **なぜ起きたか**：編集ガードの対象を、生成コード・秘密情報・ロックファイルから決めた。ハーネス自身を守る対象に入れていなかった
- **層**：基底
- **行き先**：フック（`guard-edit.sh` の対象に足す）。プロジェクトでハーネスを直すのは人、という線引きになるので、先に合意が要る
- **根拠**：0 件（机上で見つけた穴）
- **反映**：未

### 2026-11-14 試験表を回して初めて、効いていないガードが見つかった

- **出どころ**：このリポジトリ。[ガード修正の PR](https://github.com/hitoshiichikawa/agent-dev-harness/pull/2)
- **何が起きたか**：Windows パターンは 2 本の編集ガードを `&&` でつないでいて、2 本目に入力が渡らず、`.env` や生成コードの編集が素通しだった。web の `goose` の規則は、Taskfile 自身の書き方（`goose -dir ... up`）を止められなかった。どちらも目で読んだレビューでは見落とし、試験表で落ちて分かった
- **なぜ起きたか**：ガードは「止めるはず」と思って書かれ、止まることを確かめる手段が無かった。止まらないガードは、動かしても何も起きないので気づけない
- **層**：基底
- **行き先**：構造（`tests/run.sh` と試験表。各パターンを組み立て、設定の呼び出しをそのまま実行する）
- **根拠**：1 件（このリポジトリ）。同じ試験で 2 つの不具合が出た
- **反映**：済（上の PR）

### 2026-11-14 フックが Claude Code の仕様を外していて、止めているつもりの操作が止まっていなかった

- **出どころ**：このリポジトリ。公式文書の確認と、実際の Claude Code での再現。[ガード修正の PR](https://github.com/hitoshiichikawa/agent-dev-harness/pull/2)
- **何が起きたか**：3 つ。フックを相対パスで呼んでいたので、エージェントが `cd` した後は全フックが見つからなかった。ガードが途中で落ちると終了コード 1 になり、続行扱いだった。編集後の注意喚起は終了コード 0 の stderr に出していて、エージェントに届いていなかった
- **なぜ起きたか**：フックは現在のディレクトリで実行される、止めるのは終了コード 2 だけ、終了コード 0 の stderr はモデルに渡らない、という仕様を確かめずに書いた。どれも「エラーにならず、ただ効かない」壊れ方をする
- **層**：基底
- **行き先**：構造（設定の呼び出しを `${CLAUDE_PROJECT_DIR}` 基準にする。ガードは動けないとき止める）と、文書（`common/README.md`「フックを書くときの決まり」）
- **根拠**：1 件（このリポジトリ）。修正前後を実機で比べた
- **反映**：済（上の PR）

### 2026-11-04 既存システムの隣に作ると、エージェントが既存の壊れ方まで真似る

- **出どころ**：旧 FMS（車両管理 SaaS）の本体と、そのスマホアプリ版。測り方と実測値は [`common/brownfield.md`](../common/brownfield.md)
- **何が起きたか**：業務ロジックをコピーして分岐させる、判定をクライアントで再実装する、時刻変換を画面ごとに書く、ロールや種別を文字列で直書きする。新しく書いたアプリ側でも、半月で同じ壊れ方が始まっていた
- **なぜ起きたか**：エージェントは既存コードの流儀に合わせる。流儀がコピーで増やす形だと、それに合わせて増やす。「どこに定義があるべきか」が示されていないと、無いときに直書きする
- **層**：基底（原則）と、タイプ（置き場所の名指し）
- **行き先**：CLAUDE.md（`common/CLAUDE.md`「唯一の定義場所」と、web・mobile の置き場所の表）、チェックリスト（完了の定義に契約と相手側の更新を追加）
- **根拠**：1 件（仮説）。旧 FMS だけ
- **反映**：済（[唯一の定義場所の PR](https://github.com/hitoshiichikawa/agent-dev-harness/pull/1)）
