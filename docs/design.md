# 設計方針

README は「どう使うか」を書く。この文書は、このリポジトリが **なぜこの形で、どこへ向かうか** を書く。
2026-11 の議論で決めたことの記録。実プロジェクトで確かめていないものと、まだ決めていないものは 9 章に分けてある。

## 1. 目的

AI エージェントによる開発を、再現性高く成功させるためのノウハウを **ここ 1 か所に集める**。
あらゆる開発をここから始め、各プロジェクトで得た知見と失敗をここに戻す。

提供するものは、性質の違う 3 つの部品に分かれる。

| 部品 | 実体 | 寿命 |
|---|---|---|
| スケルトン | 各パターンの `template/` と README の決定事項 | 最初に 1 回コピーし、以後はプロジェクトごとに分岐する |
| ハーネス（制約と検証） | `CLAUDE.md`、`.claude/`、`check` コマンド | 導入後も更新を届けたい |
| 知見の蓄積 | README「ハーネス自体の育て方」、`common/brownfield.md` | 成果物ではなく運用の流れ |

「ハーネス」はこのうちの 1 つで、全体ではない。

進め方は、まずハーネスを固め、作ったプロジェクトの知見を戻す、の順。
机上で規約を磨いても最初の scaffold で崩れるので、「固める」は次の 3 つに絞る。残りは 1 本目のプロジェクトで潰す。

- scaffold して `check` が緑になる
- ガードに試験がある
- 知見を戻す経路が決まっている

## 2. 継承の構造

**汎用の基底 → タイプ → プロジェクト** の 3 段で継承する。README の 4 層モデルでは、基底が A 層、タイプが B・C 層、プロジェクトが D 層にあたる。

- **基底は「各タイプが必ず埋める項目の一覧」** とする。共通の文章を置くだけだと、派生側が何を用意すべきかが暗黙になり、埋まり方がばらつく。項目は次のとおり
  - 完了条件のコマンド（`check`）と、その中身
  - 生成コードの再生成コマンドと、鮮度の検査
  - 人間だけが叩く操作の一覧
  - 「唯一の定義場所」の表（そのタイプでの置き場所）
  - 確認手段（ローカル起動、スクリーンショットなど）
  - 人が確認する点（5 章）
- **原則は上に、具体は下に** 置く。知見は「それが真である一番上の層」に入れる。基底が原則を宣言し、タイプが場所を名指しする（`mobile-flutter/CLAUDE.md` の「このパターンでの置き場所」の表が手本）
- **中間層は作らない**。mac と Windows には共通部分があるが、タイプが 4 つのうちは管理の手間が上回る

木構造に収まらないものが 2 つある。

- **組み合わせ**：実際のシステムは複数タイプの合成になる。「契約を変えたら相手側も直す」のような知見は、どのタイプにも属さず、タイプ間の関係に属する（3・4 章）
- **状況**：既存システムの隣に作る（brownfield）のはタイプではなく状況で、どのタイプにも重ねる

## 3. コンポーネントと IF

開発の単位は **IF（契約）で区切ったコンポーネント** とする。全体を統括するエージェントは各コンポーネントの内部に介在せず、IF を責任分界にする。
理由はコンテキスト。担当は自分の中身と契約だけ、統括は契約と各コンポーネントの状態だけを持てば足りるので、大きなシステムでも破綻しない。

IF は 2 種類ある。

| IF | 中身 | 今の実体 |
|---|---|---|
| コンポーネント間 | API 契約 | `openapi/openapi.yaml` |
| 統括とコンポーネントの間 | 中を見ずに状態を知る手段 | 全タイプ共通の `check` の成否（2 章の項目一覧） |

「内部に介在しない」が成り立つ条件は 3 つ。

1. **契約が形だけでなく意味まで持つ**。どちらが判定するか、時刻の形式は何か、を契約側に書き、契約テストで確かめる。型として正しい IF を意味がすり抜けるのが典型的な壊れ方（`common/brownfield.md` の旧 FMS の例）
2. **契約の持ち主が統括側にある**。コンポーネントの担当は契約を直接書き換えず、変更を依頼する
3. **統括の階層にも完了の定義がある**。誰も中を見ないと、IF の設計ミスは結合するまで見つからない。統括は契約テストと結合の smoke テストを、自分の `check` として持つ

境界は、物理的にすでに分かれている所（サーバー、Web フロント、モバイルアプリ）に置く。境界は後から動かすコストが高い。
サーバー内部のドメイン分割は、「`internal/<domain>` 同士は直接 import しない」のような lint レベルの規約で足りる。

## 4. リポジトリの分け方

目安は **リリースの周期が同じなら同居、違うなら分ける**。

- API と Web フロントは一緒にデプロイするので、同じリポジトリに置く（今の web パターン）
- モバイルは別のリポジトリにする。古い版が利用者の手元に残るので、どのみちサーバーは後方互換を守る必要があり、契約変更と両側の対応を 1 つの PR にまとめる利点が小さい。関係ない側のコードを読んでコンテキストとコストを使うことも避けられる
- 分けたあとは、1 リポジトリ = 1 タイプ = 1 エージェントの責任範囲、を保つ

統括用のリポジトリは **最初からは作らない**。統括の「層」は最初から持ち、条件が来たらリポジトリに昇格させる。
条件は規模ではなく、契約を使うリポジトリの数で決める。

| 段階 | 構成の例 | 契約の置き場所 | 人が見る場所 |
|---|---|---|---|
| 0 | 1 リポジトリ（API と Web） | リポジトリ最上位の `openapi/` | 1 つの PR に契約と両側が入る |
| 1 | 2 リポジトリ（サーバーとモバイル） | サーバー側。モバイルは版を取り込み、ずれたら `check` が落ちる | サーバー側の PR。相手側の対応状況を本文に書く |
| 2 | 3 つ以上、または契約の持ち主が 1 つに決まらない | 統括用リポジトリ（契約、コンポーネント間の規約、結合の smoke テスト） | 統括用リポジトリの契約変更 PR |

- 段階 0 が既定
- 段階 1 で 3 つ目のリポジトリを作らないのは、2 つを統括するために見る場所を 3 つに増やすと、かえって人の目が届きにくくなるため
- 統括用リポジトリの雛形は、段階 2 にあたる最初のプロジェクトで作る。検証する実プロジェクトなしに雛形を置かない

## 5. 人が確認する場所

**人は個別の実装には介在しないことを標準とする。** 統括エージェントと同じく、人の確認点も IF に置く。
リポジトリを分けると 1 つの差分で全体を眺めることはできなくなるので、代わりに人が見る場所を決めておく。

- 人が必ず読むのは **契約の差分**
- 各コンポーネントの中身は、`check` と結合の smoke テストで機械的に確かめる。人は抜き取りで見る
- 契約変更の PR から、各コンポーネントの PR と状態をたどれるようにする
- 破壊的操作（デプロイ、マイグレーションの適用、署名、強制 push）は人間が叩く。DB スキーマの変更など `common/CLAUDE.md`「確認を取るべき判断」に挙げたものは、従来どおり人に確認を取る

この標準が成り立つのは、機械判定が信頼できる場合に限る。
また、人が実装を見ないことを是とできるかは、ガバナンス（責任の所在、監査、品質保証の説明）の問題を含む。組織やプロジェクトによっては標準どおりにできない。その判断はこの文書の外にある（9 章）。

## 6. 知見の入れ方

知見は足すほど良くなるわけではない。`CLAUDE.md` は足すほど 1 行あたりの効きが落ちる。
入れる先を、効きの強い順に毎回決める。

1. スケルトンの構造で、間違えようがなくする
2. lint やフックで機械的に止める
3. `CLAUDE.md` に 1 行足す
4. 人間用のチェックリストに足す

- どのプロジェクトで得た知見かを残す。1 件だけの知見は仮説として扱い、2 件目で確かめる
- 記録の書式と、プロジェクトからここへ戻す流れは [`learnings.md`](learnings.md)
- 効いていない行は削る
- **保管する場所と、毎回読ませるものを分ける**。全部をここに貯めても、全部を毎セッション読ませるわけではない。常に読ませるのは `CLAUDE.md` だけにし（1 ファイル 200 行未満が目安）、特定のファイルに関わる規約は対象を触ったときだけ、手順や参考資料は必要なときだけ読まれる形にする（7 章）

## 7. Claude Code の仕様から来る制約

2026-11-14 に公式文書で確認した内容。版が進むと変わりうるので、設計を変える前に該当ページを見直す。

| 仕様 | 設計への帰結 |
|---|---|
| プロジェクトの `settings.json` は、起動したディレクトリのものだけが読まれる。親ディレクトリからの継承も、他ファイルの取り込みも無い | 基底の設定は、プロジェクト内では複製するしかない |
| 設定を共有する手段は、ユーザー設定かプラグイン。リスト型の項目（`permissions.deny` など）は層をまたいで合算され、deny はどの層にあっても優先される | 基底のフックはプラグインで配れる。導入済みのプロジェクトにも更新が届く |
| プラグインはフック・スキル・サブエージェント・実行ファイルを配れるが、プラグイン内の `CLAUDE.md` は読まれない | 文章の規約は `@` での取り込みのまま残る |
| `CLAUDE.md` を `@` で分割しても読み込み量は減らない。`.claude/rules/` の `paths` 付きルールは該当ファイルを触ったときだけ、スキルは必要なときだけ読まれる | 6 章「保管と読み込みを分ける」の実現手段になる |
| 追加ディレクトリ（`--add-dir`）はファイルアクセスを与えるだけで、追加先のフックと権限は効かない | 統括が追加ディレクトリ経由でコンポーネントを編集すると、そのガードが効かない。統括は契約を読むだけにする |
| サブエージェントは親の作業ディレクトリで動き、別のリポジトリは指定できない。リポジトリごとに起動したセッションは、そのディレクトリの設定を読む | コンポーネントの作業は、リポジトリごとのセッションに渡す |
| クラウドで複数リポジトリを開いたセッションでは、各リポジトリのフックと権限は効かない | 複数リポジトリの統括はローカルで動かす |
| Bash の deny ルールは、公式文書自身が「セキュリティ境界ではない」としている | ガードは事故を防ぐガードレール。越えられない境界は、認証情報を持たせない・ブランチ保護をかけるなど権限側で作る |

出典：[settings](https://code.claude.com/docs/en/settings.md)、[permissions](https://code.claude.com/docs/en/permissions.md)、[memory](https://code.claude.com/docs/en/memory.md)、[large-codebases](https://code.claude.com/docs/en/large-codebases.md)、[plugins/components](https://code.claude.com/docs/en/plugins/components.md)、[sub-agents](https://code.claude.com/docs/en/sub-agents.md)、[agent-view](https://code.claude.com/docs/en/agent-view.md)

## 8. 方針と現状の差

方針に対して、このリポジトリがまだ追いついていない点。

| 方針 | 現状 |
|---|---|
| 完了は機械判定 | 終了時の門番（`check-gate.sh`）が、編集後に `check` が通っていなければ止める。残る差は 4 つ。見ているのは Edit / Write での編集だけで、Bash だけで書き換えた場合は対象外。同じ中身で 2 回目に終わると、警告つきで通る。各パターンの `check` に足した記録の 1 行は、本物の `check` の中では走らせていない。CI の雛形は無い |
| scaffold して `check` が緑になる | `template/` は実ビルドで検証していない |
| 基底は項目の一覧 | `common/` は共通の文章のまま。「唯一の定義場所」の表があるのは mobile だけ |
| `CLAUDE.md` は毎回間違えることだけに絞る | 一般論（早期 return、1 関数 1 責務など）が残っている |
| 知見は出どころを残し、行き先を決めて入れる | 受け口（`learnings.md`）はあるが、実プロジェクトからの記録はまだ無い。`common/brownfield.md` には旧 FMS の記録と規約が混ざったまま |
| ハーネスは導入後も更新を届ける | 導入は手動の `cp`。`settings.json` はパターンごとの複製で、すでにずれがある |
| 契約は意味まで持つ | 契約が持つのは OpenAPI の型と `format`（時刻は `date-time`）まで。どちらが判定するかを書く場所と、契約テストが無い |
| 段階 1 では、契約がずれたら `check` が落ちる | mobile の `gen-check` が見るのは、手元の契約と生成コードのずれだけ。手元の契約がサーバー側の版と一致しているかは見ていない |

## 9. 決めていないこと、確かめていないこと

- **人が実装に介在しないことの是非**。5 章は検討段階の標準で、ガバナンス上これを是とできるかは決めていない
- 4 章の段階表は、実プロジェクトで試していない
- 統括エージェントが複数のセッションを動かす運用は、仕組みがあることを公式文書で確認しただけで、試していない
- 基底のフックをプラグインで配るかは未決。プラグインで権限ルールまで配れるか、クラウド実行でプラグインが読まれるかは未確認
- どのタイプにも当てはまらない開発（バッチ、CLI など）は基底だけを継承する。基底が単体で使えるかは確かめていない
